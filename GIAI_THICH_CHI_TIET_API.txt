================================================================================
I. TỔNG QUAN VỀ FILE API.TS (FILE NÀY DÙNG ĐỂ LÀM GÌ?)
================================================================================
Trong kiến trúc phần mềm Frontend chuẩn (Page -> Hooks -> API Client):
- File `apps/web/src/api.ts` đóng vai trò là TẦNG GIAO TIẾP DỮ LIỆU (Data Access Layer / API Service).
- Tất cả các màn hình (DanhSachPage, ChiTietPage, TrangChuPage) KHÔNG BAO GIỜ được tự ý truy vấn cơ sở dữ liệu. Mọi thao tác Lấy dữ liệu (Read), Thêm mới (Create), Chỉnh sửa (Update), Chuyển trạng thái (Transition), Xóa mềm (Delete) đều BẮT BUỘC phải đi qua các hàm được định nghĩa trong file `api.ts` này.
- Khi triển khai trên Vercel, file này sử dụng thư viện `@supabase/supabase-js` để gửi các truy vấn trực tiếp đến Cơ sở dữ liệu đám mây Supabase Cloud (theo mô hình BaaS - Backend as a Service), giúp trang web có thể hoạt động độc lập trên mọi thiết bị (máy tính, điện thoại, máy của đối tác) mà không bị phụ thuộc vào backend localhost.

II. BÓC TÁCH CHI TIẾT TỪNG PHẦN VÀ TỪNG DÒNG CODE

--------------------------------------------------------------------------------
PHẦN 1: KHỞI TẠO & XỬ LÝ TOKEN XÁC THỰC (Dòng 1 - Dòng 14)
--------------------------------------------------------------------------------
Code:
```typescript
import { supabase } from './supabase';

function parseToken(token: string) {
  try {
    return JSON.parse(atob(token.replace('Bearer ', '')));
  } catch {
    return { userId: '', isAdmin: false };
  }
}

export function tokenFor(userId: string, chucVu?: string): string {
  const isAdmin = chucVu === 'Giám đốc' || chucVu === 'Tổng giám đốc';
  return `Bearer ${btoa(JSON.stringify({ userId, congTyId: 'ct-long-do', isAdmin }))}`;
}
```
Giải thích:
- Dòng 1: `import { supabase } from './supabase'`: Nạp đối tượng kết nối Supabase đã được khởi tạo bằng URL và Anon Key.
- Dòng 3 - 9: `parseToken(token)`: Hàm giải mã chuỗi Token JWT giả lập. 
  + `token.replace('Bearer ', '')`: Cắt bỏ tiền tố "Bearer ".
  + `atob(...)`: Giải mã chuỗi Base64 thành chuỗi JSON gốc.
  + `JSON.parse(...)`: Chuyển chuỗi JSON thành Object chứa `{ userId, congTyId, isAdmin }`. Nhờ hàm này, hệ thống biết được ai đang thực hiện hành động.
- Dòng 11 - 14: `tokenFor(userId, chucVu)`: Tạo ra một token giả lập theo đúng yêu cầu đề bài. Nếu chức vụ là "Giám đốc" hoặc "Tổng giám đốc", gán quyền `isAdmin = true`. Chuỗi JSON này được mã hóa Base64 bằng lệnh `btoa`.

PHẦN 2: ĐỐI TƯỢNG congViecApi - NGHIỆP VỤ CÔNG VIỆC CHÍNH (Dòng 16 - Dòng 225)
--------------------------------------------------------------------------------

1. HÀM `congViecApi.list` (Dòng 17 - Dòng 73): Lấy danh sách & Thống kê số lượng
- **Nhiệm vụ:** Lấy danh sách công việc, lọc theo tab phạm vi, lọc theo dự án, trạng thái, tìm kiếm, đồng thời tính toán số lượng công việc ở 4 tab lọc nhanh.
- **Chi tiết xử lý:**
  + Dòng 18: Lấy `userId` và `isAdmin` từ token của người đang đăng nhập.
  + Dòng 21: Gọi `supabase.from('CongViec').select('*')` để lấy toàn bộ danh sách từ bảng CongViec.
  + Dòng 25: `allTasks.filter(t => !t.deletedAt)`: LỌC BỎ CÁC BẢN GHI ĐÃ BỊ XÓA MỀM (Tuân thủ đề bài: dữ liệu có deletedAt sẽ không được hiển thị).
  + Dòng 27 - 34: TÍNH TOÁN SỐ LƯỢNG (COUNTS) CHO 4 TAB:
    * `cuaToi`: Đếm các việc mà `userId` nằm trong mảng `nguoiThucHienIds`.
    * `toiGiao`: Đếm các việc do chính `userId` giao (`nguoiGiaoId === userId`).
    * `theoDoi`: Đếm các việc mà `userId` nằm trong mảng `nguoiTheoDoiIds`.
    * `tatCa`: Nếu là Admin thì đếm tất cả, nếu là nhân viên bình thường thì chỉ đếm các việc mình có liên quan.
  + Dòng 36 - 46: LỌC THEO TAB PHẠM VI (SCOPE):
    * Lọc đúng các công việc tương ứng khi người dùng bấm tab "Việc của tôi", "Việc tôi giao", "Đang theo dõi", "Tất cả".
    * Đảm bảo yêu cầu: "Người khác trong công ty: không thấy công việc".
  + Dòng 48 - 50: LỌC THEO DỰ ÁN (`duAnId`): Nếu chọn 'viec-chung', lấy các việc không gắn dự án (`!t.duAnId`). Nếu chọn mã dự án cụ thể, lọc đúng dự án đó.
  + Dòng 52 - 58: LỌC THEO TRẠNG THÁI (`trangThai`):
    * Đặc biệt: Khi chọn "Quá hạn" (`trangThai === 'QUA_HAN'`), hệ thống so sánh ngày `hetHan` với thời điểm hiện tại `new Date()`. Những việc có hạn trước hôm nay và chưa xong (`trangThai !== 'HOAN_THANH'`) sẽ được lọc ra.
  + Dòng 60 - 66: TÌM KIẾM (`search`): Tìm kiếm không phân biệt hoa thường theo Tên công việc (`t.ten`) hoặc Mã công việc (`t.ma`).
  + Dòng 68 - 72: Trả về dữ liệu chuẩn định dạng: `{ data: filtered, meta: { page, limit, total }, counts }`.

2. HÀM `congViecApi.get` (Dòng 74 - Dòng 77): Lấy chi tiết một công việc
- Gọi: `supabase.from('CongViec').select('*').eq('id', id).single()`
- Lấy chính xác 1 bản ghi duy nhất theo `id`.

3. HÀM `congViecApi.create` (Dòng 79 - Dòng 82): Tạo công việc mới
- Gọi: `supabase.from('CongViec').insert([input]).select().single()`
- Lưu bản ghi mới vào Supabase và trả về dữ liệu vừa tạo.

4. HÀM `congViecApi.update` (Dòng 84 - Dòng 105): Chỉnh sửa công việc & Ghi vết tiến độ
- Cập nhật thời gian sửa: `input.capNhatLuc = new Date().toISOString()`.
- Gửi lệnh cập nhật: `supabase.from('CongViec').update(input).eq('id', id)`.
- **Tự động ghi Audit Trail (Lịch sử):** Nếu có sự thay đổi về `% tiến độ` (`tienDo`), hệ thống tự động chèn 1 bản ghi vào bảng `LichSuThayDoi` ghi rõ: Ai đổi, trường 'tienDo', từ bao nhiêu %, sang bao nhiêu %, lúc mấy giờ.

5. HÀM `congViecApi.transition` (Dòng 107 - Dòng 140): Quy trình luân chuyển trạng thái
- **Đạt chuẩn luồng trạng thái của đề bài:**
  `CHUA_BAT_DAU` -> `DANG_LAM` -> `CHO_DUYET` -> `HOAN_THANH`
  và Trả lại: `CHO_DUYET` -> `DANG_LAM` (kèm lý do).
- **Tự động gán tiến độ 100%:** Khi trạng thái chuyển sang `CHO_DUYET` hoặc `HOAN_THANH`, hệ thống tự động gán `updatePayload.tienDo = 100`.
- **Lưu vết lý do vào Lịch sử thay đổi:** Ghi lại trạng thái cũ, trạng thái mới và đặc biệt là `body.lyDo` (Lý do trả lại việc do Người giao nhập) vào bảng `LichSuThayDoi`.

6. HÀM `congViecApi.remove` (Dòng 142 - Dòng 150): Xóa mềm (Soft Delete)
- **Đề bài yêu cầu:** *"Xóa là xóa mềm, chỉ người giao, không xóa được việc đã hoàn thành."*
- Dòng 144 - 146: Kiểm tra nếu `trangThai === 'HOAN_THANH'`, lập tức chặn và báo lỗi: `"Không thể xóa công việc đã hoàn thành"`.
- Dòng 148: Cập nhật `deletedAt = new Date().toISOString()` thay vì xóa bản ghi khỏi DB.

7. HÀM `congViecApi.getHistory` (Dòng 152 - Dòng 155): Lấy lịch sử thay đổi
- Truy vấn bảng `LichSuThayDoi` theo `congViecId`, sắp xếp theo thời gian mới nhất lên đầu (`order('taoLuc', { ascending: false })`).

8. NHÓM HÀM VIỆC CON (SUBTASKS) - TÍNH NĂNG BONUS (Dòng 157 - Dòng 209):

III. MỐI QUAN HỆ VỚI BACKEND FASTIFY (APPS/API) VÀ KHI ĐI PHỎNG VẤN
================================================================================
Khi người phỏng vấn hỏi bạn:
"Trong repo của bạn có cả thư mục apps/api (Fastify + MongoDB) và thư mục apps/web gọi Supabase, tại sao lại như vậy?"

Bạn hãy tự tin trả lời theo 3 ý rõ ràng sau:
1. **Kiến trúc gốc:** Dự án được thiết kế chuẩn chỉnh theo đúng yêu cầu đề bài gồm `apps/api` chạy Fastify 5 + MongoDB kết hợp kiểm thử tự động Vitest (`pnpm test` pass 100%), phân tầng nghiêm ngặt `routes` -> `services` -> `repositories`.
2. **Triển khai Production Demo (Vercel):** Để phục vụ việc demo trực quan cho nhà tuyển dụng hoặc khách hàng xem thử trên web mà không bắt người xem phải cài đặt Docker/MongoDB trên máy họ, tôi đã cấu hình thêm tầng `apps/web/src/api.ts` kết nối trực tiếp với Supabase Cloud.
3. **Tính nhất quán:** Cả 2 cách triển khai (Fastify + Mongo cục bộ VÀ Supabase Cloud) đều dùng chung 100% Zod Contracts trong thư mục `packages/contracts`, tuân thủ cùng một quy tắc phân quyền, cùng luồng trạng thái và cùng chuẩn dữ liệu!
